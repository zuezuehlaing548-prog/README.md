과제 05: 순차 탐색과 이진 탐색 트리(BST) 탐색 비교

1. 제출 파일

| 파일 | 설명 |

| `test5.c` | C 소스 코드 (포인터를 이용한 BST 연결 구조) |
| `test5.txt` | 프로그램 실행 결과 전체 (seed = 1790736282) |
| `README.md` | 실행 결과 분석 (이 문서) |

2. 컴파일 및 실행 방법

```bash
gcc -Wall -Wextra -O2 test5.c -o test5
./test5              # seed = 현재 시각 (실행할 때마다 데이터가 바뀜)
./test5 1790736282   # seed를 직접 지정 (이 README와 같은 결과)
```

프로그램은 실행할 때 사용한 seed를 맨 위에 출력합니다. 이 README의 숫자는 모두 seed 1790736282로 실행한 결과(test5.txt)입니다. 처음에는 실행할 때마다 숫자가 달라져서 당황했는데, 현재 시각을 seed로 쓰기 때문이라는 것을 알게 되었습니다. 그래서 seed를 직접 지정할 수 있게 했습니다. 참고로 `rand()`는 운영체제마다 구현이 달라서, macOS에서 실행한 이 결과가 다른 환경에서는 같은 seed로도 다르게 나올 수 있습니다.

3. 구현 방법

- 0~1,000 사이의 서로 다른 정수 100개를 만들었습니다. 이미 나온 값이 다시 나오면 버리고 새로 만들었습니다. 만든 순서 그대로 배열에 저장했고 정렬은 하지 않았습니다.
- 같은 100개를 같은 순서로 BST에 하나씩 삽입했습니다. 노드는 `data`, `left`, `right` 세 가지로 구성했습니다.
- 탐색 대상 50개는 0~1,000 사이에서 따로 만들었습니다. 탐색 대상은 중복되어도 되기 때문에 중복 검사는 하지 않았습니다. (실제로 44가 두 번 나왔습니다.)
- 50개의 탐색 대상마다 순차 탐색과 BST 탐색을 모두 했고, 두 방법의 성공/실패 결과가 같은지 확인하는 코드도 넣었습니다.
- **비교 횟수를 세는 방법**
  - 순차 탐색: 배열 원소를 하나 볼 때마다 1회
  - BST 탐색: 노드를 하나 방문할 때마다 1회 (한 노드에서 같다/작다/크다를 판단하는 것을 1회로 셈)
  - BST 생성: 새 값을 기존 노드와 비교할 때마다 1회 (첫 번째 값은 루트가 되므로 0회)

## 4. 실행 결과 (seed = 1790736282)

| 항목 | 순차 탐색 | BST 탐색 |
|---|---|---|
| 총 비교 횟수 (50회) | **4,556** | **390** |
| 평균 비교 횟수 | **91.12** | **7.80** |
| 최대 비교 횟수 | 100 | 12 |
| 탐색 성공 평균 (6건) | 26.00 | 5.67 |
| 탐색 실패 평균 (44건) | 100.00 | 8.09 |

- BST 생성 과정의 총 비교 횟수: **614회** (첫 삽입은 0회이므로 실제 비교가 있었던 99번의 삽입 기준 평균 약 6.20회)
- 생성된 BST의 높이: **14** (노드 100개일 때 가능한 최소 높이는 7)
- 50개 탐색 대상 중 성공 6건, 실패 44건

5. 분석
5.1 두 탐색 방법의 성능 차이

BST 탐색이 순차 탐색보다 비교를 훨씬 적게 했습니다. 총 비교 횟수는 4,556회와 390회로 약 11.7배 차이가 났고, 평균은 91.12회와 7.80회였습니다.

이유는 한 번 비교했을 때 줄어드는 탐색 범위가 다르기 때문이라고 생각합니다.

- 순차 탐색은 한 번 비교하면 후보가 원소 1개만 줄어듭니다. 그래서 데이터 개수 n에 비례하는 O(n)입니다. 이번 실험에서 없는 값을 찾은 44번은 모두 배열 100개를 끝까지 봐서 정확히 100회였습니다.
- BST 탐색은 한 번 비교하면 왼쪽 또는 오른쪽 서브트리 하나를 통째로 버립니다. 그래서 비교 횟수가 트리의 높이에 비례하고, 트리가 균형에 가까우면 O(log n)입니다. 이번 실험의 최대 비교 횟수는 12회였고, 트리 높이(14)보다 작았습니다. 50개의 탐색 대상 중에 트리의 가장 깊은 곳까지 내려간 것이 없었기 때문이라고 이해했습니다.

5.2 탐색 성공과 실패의 차이

순차 탐색은 성공하면 값이 있는 위치까지만 보면 되므로 성공 6건의 평균이 26.00회였습니다. 실패하면 항상 100회입니다. 특이하게 655는 배열의 4번째 원소라서 순차 탐색도 4회, BST 탐색도 4회로 같았습니다.

BST는 성공 평균이 5.67회, 실패 평균이 8.09회로 실패가 더 많았습니다. 성공한 탐색은 값이 있는 노드에서 멈추지만, 실패한 탐색은 빈 포인터를 만날 때까지 끝까지 내려가야 하기 때문이라고 생각합니다. 다만 성공이 6건뿐이라서 이 차이를 일반적인 결과라고 말하기는 어렵습니다.

처음에는 순차 탐색 평균이 50 정도 나올 줄 알았는데 실제로는 91.12가 나와서 놀랐습니다. 이유를 생각해 보니 저장된 값은 100개인데 탐색 대상의 범위는 1,001개(0~1,000)라서, 탐색 대상이 존재할 확률이 약 10%밖에 안 되기 때문이었습니다. 그래서 50개 중 44개가 실패였고, 순차 탐색 평균이 최악의 값인 100에 가까워졌습니다. 탐색 대상이 대부분 존재하는 값이었다면 순차 탐색 평균은 대략 50 근처였을 것이라고 생각합니다. (이 부분은 직접 측정한 것이 아니라 추측입니다. 성공 6건의 평균은 26.00이었지만 건수가 적어서 참고용입니다.)

5.3 BST 생성 비용을 포함한 비교

배열은 값을 순서대로 저장만 하면 되므로 생성할 때 비교가 필요 없습니다. 반면 BST는 삽입할 위치를 찾느라 614회의 비교가 필요했습니다.

| 구분 | 순차 탐색 (배열) | BST |
|---|---|---|
| 생성 비용 | 0 | 614 |
| 50회 탐색 비용 | 4,556 | 390 |
| **합계** | **4,556** | **1,004** |

생성 비용을 포함해도 BST가 3,552회 적게 비교했습니다(약 4.5배). 탐색 한 번당 평균 (4,556 − 390) / 50 = 83.32회를 아끼므로, 생성 비용 614회를 회수하려면 614 / 83.32 ≈ **7.4회**, 즉 약 8번 탐색하면 BST가 이득이 됩니다. 반대로 데이터를 몇 번만 찾고 끝난다면 BST를 만드는 비용이 더 클 수 있습니다. 같은 데이터를 여러 번 탐색할 때 BST가 의미가 있다는 것을 알 수 있었습니다.

5.4 BST 구조에 따른 탐색 성능
BST의 탐색 비용은 트리의 높이(모양)에 따라 달라지고, 트리의 모양은 삽입 순서에 따라 달라집니다.

이번에 만들어진 트리의 높이는 14였습니다. 100개 노드로 만들 수 있는 최소 높이 7보다는 꽤 높아서 완벽하게 균형 잡히지는 않았지만, 랜덤 순서로 넣었기 때문에 극단적으로 한쪽으로 치우치지도 않았습니다. 그래서 평균 비교 횟수가 7.80회로, log2(100) ≈ 6.6보다 조금 큰 정도였습니다.

만약 1, 2, 3, …, 100처럼 정렬된 순서로 삽입하면 트리가 오른쪽으로만 자라서 연결 리스트 모양(높이 100)이 됩니다. 이 경우 탐색은 순차 탐색과 같은 O(n)이 되고, 생성 비용도 0+1+…+99 = 4,950회가 됩니다. 이는 이번 순차 탐색 50번의 비용(4,556회)보다도 많아서 BST의 장점이 완전히 없어집니다. (이 내용은 계산으로 구한 이론값이고, 이번 프로그램에서 직접 측정하지는 않았습니다.) 반대로 균형이 잘 잡힌 트리는 높이가 7이라서 최대 7번 비교로 탐색할 수 있습니다. 그래서 AVL 트리나 레드-블랙 트리처럼 균형을 유지하는 트리가 필요하다는 것도 이해할 수 있었습니다.

5.5 다른 seed로 실행한 결과비교
같은 코드를 seed만 바꿔 세 번 실행해 보았습니다. 이 README의 분석은 마지막 줄(seed 1790736282)을 기준으로 했습니다.

| seed | 순차 평균 | BST 평균 | BST 높이 | 생성 비용 | 손익분기점 |
|---|---|---|---|---|---|
| 1790731795 | 97.72 | 10.42 | 18 | 801 | 9.2회 |
| 1790735117 | 92.08 | 8.20 | 11 | 615 | 7.3회 |
| 1790736282 | 91.12 | 7.80 | 14 | 614 | 7.4회 |

세 번 모두 BST가 순차 탐색보다 약 9~12배 적게 비교했고, 생성 비용을 포함해도 BST가 유리했습니다. 다만 트리 높이가 11~18로 달라졌고, 높이가 높을수록(18) BST 평균과 생성 비용도 커졌습니다. 랜덤하게 넣어도 트리의 모양은 운에 따라 꽤 달라진다는 것을 확인했습니다.

5.6 한계
위 세 번의 실행도 표본이 적습니다. 더 많은 seed로 실행하고 평균을 내면 더 믿을 수 있을 것 같습니다.
성공한 탐색이 6건뿐이라 성공 평균은 참고용으로만 봐야 합니다.

6. 결론

1. BST 탐색의 평균 비교 횟수는 7.80회로, 순차 탐색의 91.12회보다 약 11.7배 적었습니다.
2. BST를 만드는 데 614회가 들었지만, 생성 비용을 더해도 총 1,004회로 순차 탐색 4,556회보다 적었습니다. 약 8번 이상 탐색하면 생성 비용을 회수할 수 있습니다.
3. BST의 성능은 트리 높이에 달려 있습니다. 이번 트리는 높이가 14였고, seed에 따라 11~18까지 달라졌으며, 삽입 순서가 나쁘면 O(n)까지 나빠질 수 있습니다.
